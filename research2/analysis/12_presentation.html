Transcript. So here's the setup. A human shows the robot how to do something — reach for a cube, or route around an obstacle. The robot then has to do the same task later, but the scene is different. Different colors, different camera angle, different lighting, maybe the cube is in a totally different spot. Now, behavior cloning fits the demonstrations really cleanly. But in closed loop, the policy can drift. It can hover. It can just stop. And the obvious fix — use a pretrained encoder like ResNet — well, that's not obvious either, because sim pixels aren't ImageNet. So what we wanted to figure out is: which visual axis is actually the one that breaks control?

We evaluate whether the closed-loop policy reaches the cube under held-out scenes.

Success

S@1 cm — strict S@2 cm — medium S@5 cm — broad
Closest dbest = mint ||eet − target||
Success S@r = 1[ dbest ≤ r ], r ∈ {1, 2, 5} cm
Transcript. Quick note on how we evaluate. This is closed-loop, not offline prediction. We reset PyBullet to a held-out scene, run the policy for up to 400 control steps, and we log the minimum distance to the cube across the rollout. Two splits to talk about. In-distribution — that's the same training distribution with fresh seeds — tests whether the policy memorized. Out-of-distribution — that's held-out variants on a specific axis — tests whether the policy actually generalized. And then we report three thresholds: 1 centimeter, 2, and 5. The 1-centimeter strict precision is our headline metric. The looser ones, we report them to make a point that you'll see on the next slide.

Method bridge

To address spatial OOD, we add phase + geometry to the visual BC policy.

1
Diagnose
Spatial OOD is a routing problem, not an image problem.
Color Camera Lighting Spatial — 2.9% S@1
2
Add phase
Expose which part of the route is being executed.
side_align → cube_hover → final_descent
3
Add geometry
Expose the spatial relations the pixels weren't providing.
target xyz obstacle xyz obstacle size Δ ee→tgt Δ obs→tgt
4
Compare
Same BC loss and RGB stream — only the added state varies.
visual +phase +target +geom +phase+geom
Policy at = π(Iext, Iwrist, qt, zstruct)
zstruct [phase3, target3, obs_center3, obs_size3, Δee→tgt, Δobs→tgt] — 18D
Transcript. So here's our hypothesis. Spatial OOD isn't an image problem. It's a routing problem. So we keep the visual BC setup completely fixed, and we add structure to the input. Step one here is the diagnosis we just walked through. Step two: we add phase labels. Each timestep gets one of three labels — side_align, cube_hover, or final_descent — describing what part of the route the expert is currently executing. Step three: we add geometry — an 18-dimensional vector with target position, obstacle position, the obstacle's size, and the relative deltas between things. Step four: we compare ablations. Same loss, same RGB stream, same evaluation protocol. Only the added state varies.
